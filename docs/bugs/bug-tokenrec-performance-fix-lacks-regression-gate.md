# TokenRec 性能与单实例修复缺少可重复运行门禁

## 1. 预期行为

发布前应机械证明：未变化文件在多次 refresh 中不重复解析、变化文件并发解析、安装版第二实例立即退出、固定 PID 的累计 CPU 增量处于阈值内，并且验收结束只回收本次启动的精确 PID。

## 2. 实际行为

`8353ec0` 同时加入了大部分性能实现和测试，缺少可审计的 RED 记录；现有 singleton 测试只在同一 XCTest 进程打开两个 fd。历史验收依赖瞬时 `%CPU` 和手工命令，没有脚本、固定采样窗口或可靠 trap，曾留下多个 TokenRec 进程。

## 3. 稳定复现

1. 连续运行旧的 `.build/debug/TokenRec & sleep N` 验收命令。
2. 命令结束后后台 PID 仍存活，重复运行会积累进程。
3. 单点 `ps -o %cpu` 可能恰好为 0，也可能处于解析峰值，不能证明 60 秒稳态。
4. 当前仓库不存在 `scripts/verify-installed-app.sh`，无法自动验证双开、CPU 时间增量和 teardown。

## 4. 根因

性能修复以实现和一次性人工观测为中心，没有先定义可重复的行为门禁。进程启动、ownership、采样和回收没有封装为同一脚本，测试也未验证 teardown 不会误杀无关进程。

## 5. 影响范围

缓存、并发或 timer 回退可在测试仍绿时重新引入高 CPU；单实例只在同进程语义下被覆盖。任何后续安装验收都可能再次泄漏进程或用不可复现的数据宣称通过。

## 6. 修复与验证

新增安装版验收脚本：直接启动 bundle executable 并记录 `$!`，第二次启动必须快速退出；用同一 PID 的 `ps -o time=` 在至少 60 秒窗口计算累计 CPU 增量；trap 只结束精确 PID 并等待退出。脚本自检以无关 sentinel 进程证明不会宽泛清理。Repository 测试覆盖六次静态 load、单文件追加/替换和大于 1 的并发解析数。
